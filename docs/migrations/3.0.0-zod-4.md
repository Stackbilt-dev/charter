# Charter 3.0.0: Zod 4 migration

Charter 3.0.0 moves every workspace Zod dependency to `^4.6.6` (the lockfile resolves 4.6.7). This is a **major release** because `@stackbilt/core`, `@stackbilt/blast`, and `@stackbilt/surface` export Zod schema objects and inferred types. All 13 published workspace packages advance together; no exports are removed or renamed. The private root package is not the release version authority.

The migration addresses the remaining HIGH-severity Zod advisory, [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5). The compatible dependency repairs in the prerequisite #397 PR are also required for a clean workspace audit. Scaffolded Zod dependencies now declare the same patched minimum.

## Consumer changes

- Upgrade related `@stackbilt/*` packages together. Consumers extending exported schemas should use Zod 4, rather than mixing Zod 3 constructors or types with them.
- Read `ZodError.issues`; the `.errors` alias is gone. Issue codes, issue metadata, and default error messages follow Zod 4 and can differ from Zod 3. Do not depend on undocumented schema internals or exact native error text.
- Prefer `safeParse` when handling schemas across independently installed dependency trees. `instanceof ZodError` requires the same runtime constructor; a separately installed Zod 3 error is not a Zod 4 error.
- Zod 4 integer validation rejects unsafe integers, and number schemas reject non-finite numbers. Charter now rejects such programmatic payloads; JSON cannot represent Infinity or NaN. For example, blast `maxDepth` must be a positive safe integer.
- Use `.safeExtend()` rather than `.extend()` when extending a refined Zod 4 object such as `CreateLedgerEntrySchema`. Plain object exports such as `BlastInputSchema` remain extendable with `.extend()`.

```ts
import { z } from 'zod'; // Zod 4
import { BlastInputSchema } from '@stackbilt/blast';

const requestSchema = BlastInputSchema.extend({ requestId: z.string().min(1) });
const parsed = requestSchema.safeParse({ seeds: ['src/index.ts'], requestId: 'request-1' });
if (!parsed.success) {
  console.error(parsed.error.issues);
}
```

## Preserved Charter behavior

- Blast and surface defaults, unknown-key stripping, open-ended alias/histogram maps, governance defaults, project-name transforms, and notary cross-field checks retain their existing JSON shapes.
- Governance identifier fields use `z.guid()` to retain the UUID-like hexadecimal form accepted before this migration. Switching directly to Zod 4's stricter `.uuid()` would reject previously accepted identifiers solely because of their version/variant bits.
- Existing defaults are not transform-dependent, and none apply a default inside an outer optional field. They do not need `.prefault()`. Regression tests cover omitted fields, explicit undefined defaults, and absent optional `schemaPaths`.
- CLI errors retain their wrappers and exit-code meanings; the embedded human-readable native Zod messages may change. MCP tool names and advertised argument shapes remain stable, including string-valued alias records. The MCP record constructor now supplies both key and value schemas.
- Context-refresh snapshot validation is implemented by Charter's current snapshot parser, rather than the old Zod-based code referenced in #310. Its existing test suite remains part of migration validation.
- The supported Node engine declarations remain unchanged. Validate on the repository's Node 20 CI runtime before release.

For upstream details, see the [official Zod 4 migration guide](https://zod.dev/v4/changelog). This PR prepares the migration; it does not publish packages. Re-enable Dependabot's Zod-major updates only after the migration lands.
